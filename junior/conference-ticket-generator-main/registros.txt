#Desafio: Frontend Mentor - conference-ticket-generator-main

Nível: Junior
Recursos e avaliação: implementação usando claude code no terminal do vscode. Comentário: Para definir milestones e issue foi inserido o seguinte prompt: "A partir do objeto do desafio, montem uma previa para mim de planejamento para implementação levando em consideração um plano que contém milestones e que contém issues em em cada uma issue pode conter uma ou mais tarefas que são representados por sessões de implementação aqui o claude code, sendo registrado na issues a execuçãode de cada tarefa por comentários. Após eu aprovar esse plano, irei te pedir para criar as millestones e issues que irão nortear o desenvolvimento. Alguma duvida sobre essa estrutura?". Retorno do assistente: 1. Onde ficam as issues? O repositório do GitHub é compartilhado entre todos os desafios. Sugiro prefixar os milestones com conference-ticket e usar um label conference-ticket. Confirma? 2. Idioma: issues e comentários em português? 3. Branch e PR: uma branch por issue ou continuar na conference-ticket e fechar issues por commit (Closes #n)?  4. Número serial do ticket: aleatório a cada geração ou fixo (#01609)? Sugiro aleatório. 5. Persistência: o ticket deve sobreviver a recarregar a página (localStorage) ou voltar ao formulário? Sugiro não persistir. 6. Granularidade: está bom assim ou você prefere menos issues, com mais tarefas em cada?; DECISÃO: 1.Repositório: milestones e issues no repositório do GitHub do desafio, com o prefixo e o label conference-ticket, 2- Idioma: títulos, descrições e comentários em português.3- Branch: tudo na conference-ticket, sem branches por issue.4- Fechamento: ao terminar a última tarefa de uma issue, eu comento que ela está finalizada e peço a você que faça o commit e feche a issue. Eu não faço commit nem fecho issues.5- Número serial: aleatório a cada geração, com zero-padding (#01609).6 - Persistência: o ticket não persiste. Recarregar a página volta ao formulário. 7- Granularidade: 5 milestones, 14 issues e as tarefas listadas. Foi necessário instalar o gh (GitHub CLI) para gerar os milestones e issues (! sudo apt install gh e ! gh auth login). milestones e issues foram criadas. 

Fluxo da implementação: arquivo claude.md contém dois blocos, um já definido (intruções fixas) como: ## O que é isto, ## Atribuição no rodapé, ## Convenções e ## Regras do repositório e o outro é são as instruções dinâmicas geradas pelo por um prompt que pede para o assistente ler a pasta do projeto que contém os documentos fornecidos para o desafio sendo gerada as instruções para: ### Estrutura pontos de atenção que contém os itens **Arquivos**, **Design**, **Pontos de atenção**; Como foram criados as issues os prompts passaram a serguir a ordem planejada. Sendo até mesmo o setup implementado pelo assistente. Nos prompts de implementação não foram indicados somente a issues, mas também incluidos orientações de leitura de documentos e pedido de esclarecimento de duvidas que possam ocorrer utilizando o plan mode antes de implementar o codigo. Cada implementação o humano realizou o commite manualmente.
Diferente das outras praticas que foram separadas prompt para construção do HTML, prompt para o CSS e prompt para JS, as issues fatiaram em várias implementações. Foi observado necessidade de ajustes em codigo do HTML já criado em sessão anterior


Ocorrências: A várias sessão aplicadas em cada issue parecem que se tornam micro decisões, se nos desafios anteriores as sessões eram divididas por tecnologia em uso, havendo um inquerito do assistente para satisfazer duvida, neste modelos os inqueritos são poucos. Commits manuais podem ser esquecidos
